# 坑位清单

**22 条全部是实测踩出来的**，没有一条是推测。

这里记录的不是「API 文档里写了什么」，而是**文档没写、但一定会让你损失一整个下午的东西**。

> 📌 **怎么用这份文档**
> 每条包含四段：**症状**（你会看到什么）→ **根因**（为什么）→ **怎么发现**（我们如何定位）→ **怎么办**（可直接抄的做法）。
> 如果你是第一次搭，至少读 **坑 9 / 10 / 19 / 20**——那几条能直接救你一次交付事故。
>
> 验证环境：Lightroom Classic 15.3 (Windows) · `@pired/lightroom-mcp` 3.2.6 · Canon EOS R8 CR3

## 🔴 会毁掉工作的三条

<a id="pit-9"></a>
### 坑 9：`add_ai_mask` 会把 Lightroom 的目录写锁卡死（最严重）

**症状**

调用一次 `add_ai_mask` 之后，**任何**写操作全部失败——不只是这一个工具：

```
LrCatalog:withWriteAccessDo: could not execute action '...'.
It was blocked by another write access call, and no timeout parameters were provided.
```

受影响的不止是 AI 的调用：`set_develop_settings`、`set_mask_adjustments`，**甚至用户自己在 Lightroom 里手动拖滑块**也一起失效。

**而且不会自愈。** 等 100 秒、Lightroom CPU 完全空闲、重启 MCP 桥进程——统统没用。**只有重启 Lightroom 能恢复。**

**根因**

`add_ai_mask` 走的是 Develop 模块的 UI 通道（`LrDevelopController`），AI 蒙版计算在后台没有及时释放目录写锁。这是一次调用就把整个会话的写入能力赔进去。

**怎么发现**

插件日志（`<我的文档>\LrClassicLogs\LightroomMCP.log`）能坐实因果：`addAIMask('subject')` 成功那一行之后，紧接着所有写操作开始报 `blocked`。时间戳严丝合缝。

**还有一个隐藏的坑**：`add_ai_mask` 返回的 `mask_id` **可能是错的**——实测它返回了照片上**另一个人脸蒙版**的 ID。如果直接拿这个 ID 去写参数，会**覆盖掉用户自己做的修图**（磨皮、眼白、虹膜、牙齿）。

**怎么办**

1. **不要用 `add_ai_mask`。** 要做局部调整就用 `add_local_adjustment`（线性/径向渐变）——它走 `catalog:withWriteAccessDo("Add Local Adjustment")` **直接写目录，不碰 Develop 模块 UI**，没有这个风险。
2. 如果确实需要 AI 蒙版：先在 Lightroom 里手动建好蒙版，然后用 `list_masks` 读出**真实**的 mask id，再用 `set_mask_adjustments` 改参数。
3. **任何写蒙版参数之前，必须用 `list_masks` 核对名字。** 不要相信 `add_ai_mask` 返回的 id。

> 💡 想要「局部调整」的效果又不想碰蒙版？试试 [用 HSL 当免蒙版局部调整](#技巧用-hsl-当免蒙版局部调整)。

<a id="pit-19"></a>
### 坑 19：快照会静默回退照片，而且无法检测

**症状**

六张全部调完、用户逐张确认、统一导出之后，用户发现其中一张明显不对。

回查发现**两张被回退到了会话早期的废弃版本**（全零滑块 + 别的照片的曲线 + 早期色温），而回退后的状态**与当时存的 `pre-clean-reset` 快照完全一致**。

**根因**

在 Lightroom 里**点一下快照 = 直接覆盖当前所有调整，没有任何确认对话框**。而：

- SDK **不能列出快照**
- SDK **不能读取「当前应用了哪个快照」**
- 所以从 MCP 这一侧**看不出任何异常**——参数读出来是「合法的值」，只是旧的

**怎么发现**

**只能靠人眼。** 这次是用户说「这张不对吧」才发现的。在此之前，所有自动化检查（文件大小、JPEG 画质、参数回读）**全部通过**。

**更阴险的连带效应**：坑 10（`As Shot` 不还原色温）会让「重建」也对不上。重建时按真正的原始色温 3800K 写，结果与批准版差 **MAD 8.0**——因为批准版当时是在被 bug 卡住的 **3400K** 下调出来的。

> **教训：重建必须以「批准版的渲染文件」为基准做逐像素比对，不能只按记忆里的参数写。**

**怎么办（三条都要做）**

1. **命名规范**：回退用的快照一定要带警示，例如 `⚠️废弃-勿点-pre-clean-reset`。只有 `*-final` 系列是安全的。**并且要口头告诉用户。**
2. **保留参照文件**：每次用户点头时，把当次导出**另存到一个不会被覆盖的路径**，作为后续唯一的真相来源。
3. **交付前逐张验证**：把新导出与参照文件做 **MAD 比对**，而不是只看文件大小或画质。代码见 [README](../README.md#交付前必须做的验证)。

**MAD 判读**：

| MAD | 含义 | 先查什么 |
|---|---|---|
| `0.00` | 逐像素一致 ✅ | — |
| `2 ~ 10` | 有明显差异 | **先查色温**（坑 10） |
| 尺寸不同 | 裁切或角度被动过 | ⚠️ 光恢复 `CropAngle` 不够，`CropTop/Left/Bottom/Right` **也要一起恢复** |

<a id="pit-10"></a>
### 坑 10：`WhiteBalance: "As Shot"` 不会还原色温

**症状**

把色温改成 Custom 6800K 之后，再写 `{"WhiteBalance": "As Shot"}`。回读**确实显示 `"As Shot"`**——但 `Temperature` 仍然是 6800，**渲染也仍然是暖的**。

这个 bug 最坏的地方是它**让你以为已经回到原片基调了**，实际上一直在错误的色温上继续叠加。

**怎么发现**

对比「当前渲染」与「参照渲染」，MAD 是 8.0 而不是 0。逐项排查参数时才发现色温没回去。

**怎么办**

**永远显式写死相机原值**，不要依赖 `"As Shot"`：

```json
{"WhiteBalance": "Custom", "Temperature": 4800, "Tint": 7}
```

相机原值从 `get_photo_metadata` 的 EXIF 里读，或者直接看 Lightroom 里「原照设置」显示的数字。

<a id="pit-15"></a>
### 坑 15：先修曝光，再谈风格（顺序错了全白干）

**症状**

一张照片调成「冷青电影感」，肉眼觉得「差不多了」，但直方图显示：死白 **12.4%**、天空的 R−B 只有 **−4**（基本中性）——**风格根本没落地**。

**根因**

那张照片**本来就过曝了**：`p50 = 195`，意思是**一半的画面比 195 还亮**。

在已经发白的底子上刷蓝调/夕阳/渐变，只会让它从「干净的白」变成「浑浊的灰白」。**越调越糟。**

**怎么办**

**`p50` 是判断曝光的第一指标。**

| p50 | 判断 |
|---|---|
| < 110 | 偏暗，考虑提亮 |
| **110 ~ 160** | ✅ 正常（白天街头） |
| > 160 | 偏亮 |
| > 180 | **过曝，先修曝光，别碰风格** |

**正确顺序：先把 p50 修到 110~160，再谈风格。**

> ⚠️ 对比度和黑阶**只能修暗的那一端**，动不了占画面大头的亮部。不要指望用它们救过曝。

## 🟠 会让你白干一轮的

<a id="pit-3"></a>
### 坑 3：`reset_develop` 静默失败

**症状**

调用返回 `success: true`，但照片参数没变。

**根因**

`reset_develop` 走的是 Lightroom 内置的「复位」命令，**只作用于当前活动照片**。如果目标照片没有被选中，复位就打到了别处、或者落空。

**怎么发现**

**看响应里的 `before`/`after` diff，不要看 `success`。** 如果每个参数的 `before` 和 `after` 一模一样 → 没生效。

**怎么办**

```
create_virtual_copies([源id])   → 拿到新 id
select_photos([新id])           ← 必须！复位前一定要选中
reset_develop(新id, scope="all")
```

**兜底**：干脆不用复位，直接 `set_develop_settings` 把所有相关参数显式写成默认值。更啰嗦，但**永远不会静默失败**。

<a id="pit-4"></a>
### 坑 4：`select_photos` 只能选「当前视图内」的照片

**症状**

```
Selected 0 of N — "the rest are not in the current view source"
```

**根因**

Lightroom SDK 的硬限制。**MCP 没有提供切换视图源的工具**（`manage_view_filter` 只管过滤器，不管视图源）。

**连带后果**：`create_virtual_copies` 会失败并报 `attempt to index a boolean value`——因为它先选中源照片再克隆，选不中就克隆了个空选择。**报错信息完全指不到真正的原因。**

**怎么办**

让用户**手动在 Lightroom 左侧「目录」面板点「所有照片」**。这是唯一可靠的办法。把这句话写进你的排查话术里。

<a id="pit-5"></a>
### 坑 5：导出是后台任务，文件不会立刻出现

**症状**

`export_photos` 返回 `success: true`，但目标文件还是旧的（或不存在）。

**根因**

导出是异步后台任务，返回时文件可能还没写盘。

**怎么办**

**必须轮询等文件落盘**，再 `read_image`：

```powershell
for ($i=1; $i -le 25; $i++) {
  $f = Get-ChildItem $dir -File | Select-Object -First 1
  if ($f -and $f.Length -gt 1000) { break }
  Start-Sleep -Seconds 3
}
```

**否则会拿旧文件当新结果看。** 我们因此白排查了一轮——「改了参数怎么没变化？」

<a id="pit-12"></a>
### 坑 12：导出的 `width`/`height` 参数会把图变成 1000px

**症状**

传 `width: 1500`，实际输出 `1000×667`。

**根因**

在 `HandlerExport.lua` 里，只给了 `LR_size_maxWidth`，而 `LR_size_maxHeight` 是 `nil`，于是 Lightroom 套用了默认的长边 1000px。

**怎么办**

**导出时不要传 `width`/`height`。** 全尺寸导出，需要小图就本地缩放：

```powershell
# crop_image.py <输入> <输出> <left> <top> <right> <bottom> [长边像素]
# 边界传 0 0 1 1 = 不裁切，只缩放
python scripts/crop_image.py in.jpg out.jpg 0 0 1 1 1200
```

<a id="pit-16"></a>
### 坑 16：不要相信未标定的自动测量

**症状**

我们写过两个倾斜估算器——一个「主边角度直方图」法，一个「水平梯度平方和」法。两个都报告某个区域有 `+0.62°` 的一致倾斜。

**根因**

**两个都没通过标定。** 把图人为旋转 −2° ~ +2°，读数只动了 **0.15°**。所谓「三个区域高度一致的 +0.62°」**纯粹是系统偏差**，和图片内容有关，和倾斜无关。

基于这个假数据改 `CropAngle` 完全是错的，后来撤销了。

**怎么办**

> **规则：任何自动测量，必须先用已知量标定，才能用来下结论。**
> 标定不过就**老实放弃自动化**，改用别的手段。

倾斜这件事，我们最终用**参考网格叠加图 + 用户的眼睛**：

```powershell
python scripts/grid_overlay.py photo.jpg -o grid.jpg --step 100
```

两个失败脚本仍保留在仓库里（`scripts/estimate_tilt.py`、`scripts/level_check.py`），**作为反面教材**——它们的文档字符串里明确写了「标定失败，不要据它下结论」。

<a id="pit-14"></a>
### 坑 14：Lightroom 启动后插件不加载 → 让用户按 `G`

**症状**

Lightroom 在跑，但端口 58763/58764 一直不监听，日志**完全没有新行**（连 `PluginInfoProvider loaded` 都没有）。

**根因**

插件 `Info.lua` 里 `LrForceInitPlugin = true` 的前提是**至少有一个菜单项**。而这个插件只注册了 `LrLibraryMenuItems`（**图库**菜单）。

**如果 Lightroom 启动后停在「修改照片」模块，强制初始化根本不会触发，插件永远不会加载。**

**怎么发现**

日志「完全没有新行」是关键判据——说明插件**压根没被加载**，而不是端口冲突或配置错误。这两者的排查方向完全不同。

**怎么办**

1. 让用户**按 `G` 切到「图库」模块**
2. 还不行 → 「文件 > 增效工具管理器」里手动重新加载
3. 想在修改照片模块直接用 → 插件需要注册 `LrDevelopMenuItems`，那要改插件源码

<a id="pit-20"></a>
### 坑 20：报错说「别的进程占着连接」，其实是桥自己僵死了

**症状**

Lightroom 明明在跑、窗口有响应，但**每一个** MCP 工具都返回同一句话：

```
Connected to the Lightroom plugin's ports, but it is not answering.
The plugin serves one client at a time, so another lightroom-mcp process
is most likely holding the connection.
```

而且：

- 端口 58763/58764 确实处于 `LISTENING`，占用进程就是 `Lightroom.exe`
- 插件日志停在上一次启动时的 `RESPONSE bound on 58764 gen=1`，之后**一行 `Request id=` 都没有**
- 「增效工具管理器里禁用再启用插件」**没用**
- **重启 Lightroom 也没用**——因为坏的不是 Lightroom，是桥

**根因**

桥（`node .../@pired/lightroom-mcp/dist/index.js`，由 MCP 客户端以 stdio 拉起）和插件之间只有两条 TCP 连接。Lightroom 重启后，插件那头的 socket 已经不存在了，但**桥的 node socket 可能没收到 close**，于是：

1. 桥内部 `socketsConnected()` 仍为真 → 它不重连；
2. 每次工具调用前都要先 ping（`plugin-liveness.js`），ping 被写进**一条死连接**，永远等不到 pong；
3. 桥据此把插件标记成 `unresponsive`，**连正常请求都不再往下发**，直接返回上面那句话。

那句「另一个进程占着连接」是桥的**猜测**（源码里就是这个措辞），不是事实。实测那次，机器上只有一条桥（PID 5824），根本没有第二个客户端。

**怎么发现（别再靠猜）**

| 证据 | 健康时 | 僵死时 |
|---|---|---|
| 插件日志 `LightroomMCP.log` | 每次工具调用有一行 `Request id=... action=...` | **没有任何 `Request id=` 行** |
| 端口连接的端点 | 临时端口 → 插件端口：`127.0.0.1:59556 → 127.0.0.1:58763` | `127.0.0.1:58763 → 127.0.0.1:58763`（本地端口就是插件端口，等于自己连自己） |
| 直连探针 `node scripts/ping-plugin.mjs` | **先杀桥**再跑 → 秒回 `{"pong":true}` | 桥还活着时**必然**无回应（见下面那个陷阱） |

> ⚠️ **探针有个反直觉的陷阱**：插件同一时刻**只服务一个客户端**，第二个连接会被**静默忽略**（不报错、不打日志、就是没回应）。实测：桥健康连着的时候跑探针，10 秒无回应；把桥杀掉再跑，立刻回 pong。所以**探针必须在杀桥之后跑才有判定力**——「探针没回应」本身不能证明插件坏了。

### 先说清楚：`not answering` 有两种，处理方式相反

同一条报错，可能是两件完全不同的事。**判据只有一个：插件日志里有没有那一行请求。**

| | 桥僵死 | **插件被长任务占住** |
|---|---|---|
| 端口连接 | 异常（两端都是插件端口） | **正常**（临时端口 → 插件端口） |
| 插件日志 | **没有** `Request id=...` | **有**那行请求，且几秒后跟一条完成记录 |
| 该怎么处理 | **杀桥** | **等**，别杀桥 |

实测那次（不是僵死）：日志里 `18:35:34 Request id=... action=export_photos` → `18:35:41 Exported 1 photos to: ...`，7 秒完成；但 MCP 那一侧已经先报了 timeout，紧接着的第二次调用又撞上「not answering」。

> **教训**：看到 `not answering` 先 `Get-Content LightroomMCP.log -Tail 8`。
> **有请求行 = 插件在干活，等它**（导出/渲染/导入都可能几十秒）；**没有请求行 = 桥僵死，按下面杀桥**。
> 杀桥不能让正在跑的导出变快，只会把响应丢掉。

**怎么办**

1. **先杀桥，别碰 Lightroom。** 桥 PID 有两个来源：`%USERPROFILE%\.config\lightroom-mcp\bridge-58763-58764.lock`（内容就是 PID），或 `netstat -ano | findstr 58763` 里那条非 Lightroom 的 `ESTABLISHED`。

   ```powershell
   Stop-Process -Id <桥PID> -Force
   ```

2. **等 3 秒。** 由 DSH 的 `mcp-client` 托管时桥会被自动重启（默认延迟 500ms、连续失败上限 10 次）。判据：`netstat` 里出现 `127.0.0.1:<临时端口> → 127.0.0.1:58763`，工具立刻恢复。

3. 只有「杀桥 + 探针仍无回应」才去怀疑插件，那时才按 [坑 14](#pit-14) 走：按 `G` 切图库模块 → 增效工具管理器 → 重启 Lightroom。

4. **两种做法的代价差得很远**：重启 Lightroom 会丢掉你正选中的多张照片（实测：**25 张多选 → 只剩 1 张活动照片**，视图筛选器还得重设）；杀桥的代价是 **3 秒**。

> 💡 受限沙箱里 `Get-CimInstance` / `tasklist` / `Get-NetTCPConnection` 都可能 `Access denied`，能用的组合是 `netstat -ano` + `Get-Process -Id`。别因为命令被拒就以为环境坏了。

<a id="pit-21"></a>
### 坑 21：竖拍照片的裁切坐标是「旋转前」的空间

**症状**

用 `set_develop_settings` 写 `CropLeft/Top/Right/Bottom` 去裁**竖拍**照片，裁掉的方向和预期**相反**，或者导出后的宽高比完全对不上：

- 想裁掉底部 → 结果**左右**窄了 12%（4000×6000 变成 3520×6000）
- 换成 `CropRight` → 大小对了，但裁掉的是**顶部**
- 折腾两轮导出才找到对的那条边

横拍照片完全正常，所以这个坑只在竖拍上炸。

**根因**

Lightroom 存的裁切坐标是**旋转前的像素空间**。相机竖持时文件里是横向存储（本机实测：显示 4000×6000，存储 6000×4000），于是轴整个换了位：

| 你想控制 | 实际要写 |
|---|---|
| 视觉的**上 / 下** | `CropLeft` / `CropRight` |
| 视觉的**左 / 右** | `CropTop` / `CropBottom` |

实测（IMG_0316，4000×6000 竖拍）三次写入的结果：

| 写入 | 期望 | 实际 |
|---|---|---|
| `CropBottom 0.88` | 裁底部 12% | 3520×6000，裁掉了**左右** ❌ |
| `CropRight 0.88` | 裁底部 12% | 4000×5280，但裁掉了**顶部** ❌ |
| `CropLeft 0.12` | 裁底部 12% | 4000×5280，裁掉**底部** ✅ |

**怎么发现**

写完立刻导出量尺寸（`imgsize.py` 或 PIL 读一下）。**如果尺寸变化的方向和你设的比例不符**（想减高度、结果宽度变了），就是坐标轴反了——不要去调数值，先换轴。

**怎么办**

1. **先判断这张是不是旋转过的**：读 `cropAngle` / `orientation`，或者直接看导出尺寸和 `get_photo_metadata` 的 dimensions 是否一个竖一个横
2. **竖拍一律先按上表换轴**，再用「导出量尺寸」验证一次
3. 更省事的做法：**裁切让用户在 Lightroom 里拖**。裁切是纯视觉操作，人拖 2 秒；我们试错一次要 1 轮导出（约 1 分钟），而且第一轮几乎必错

> 💡 同一套坐标还影响**局部蒙版的位置**（蒙版是相对裁切后画面存的）。所以：**先定裁切，再放蒙版**。顺序反了的话，改一次裁切就得重放一次蒙版。

<a id="pit-22"></a>
### 坑 22：竖拍照片的局部蒙版会**飞到别处**，且无法用公式补偿

**症状**

在竖拍照片上 `add_local_adjustment` 放一个径向蒙版去提亮脸部，工具返回 `success: true`、`list_masks` 也能看到蒙版、`set_mask_adjustments` 改滑块同样返回"applied"——**但画面上什么也没发生**。

更糟的是：直接导出一看，**暗斑打在了别的地方**（实例：想提亮脸，结果在她胸口压出一块明显的暗椭圆）。

**根因**

竖拍照片的像素是横向存储的（显示 4000×6000，存储 6000×4000）。坑 21 说过裁切坐标在"旋转前"空间里——**局部蒙版更麻烦：x 基本正常，y 会被缩放，而且不是线性关系**，无法用一次标定推出补偿量。

实测（IMG_0372，4000×6000 竖拍，径向蒙版）：

| 请求的中心 y | 实际落点的 y 范围 | 备注 |
|---|---|---|
| 0.400 | 0.511 – 0.655（质心 0.554） | 暗斑落在胸口 ❌ |
| 0.289（按 1.385× 补偿推算） | 0.508 – 0.693（质心 0.603） | **更偏了**，证明非线性 |
| 删除 | — | 画面恢复干净 |

**怎么确认（顺序别跳）**

1. **先做决定性测试**：把蒙版曝光推到 **−1.5 EV** 再导出。画面毫无变化 → 蒙版没生效或不在视野内，**不要继续在它上面调数值**
2. **用导出做差分定位**：分别导出"改前/改后"两张，算 `abs(a-b)` 的质心——它会直接告诉你蒙版落在哪。实测一眼就看出来落点在自己没预料的地方
3. ⚠️ 差分必须**只隔离一个变量**：如果同一轮还改了全局 HSL，整张图的差异会淹没蒙版的落点（我第一次就被坑了，差异区域铺满下半张）

**怎么办**

1. **竖拍照片不要用归一化坐标放蒙版**——尤其脸、手这些位置关键的小蒙版
2. 优先用 **AI 蒙版**（`add_ai_mask` 的 subject / sky），它按内容选，不吃坐标
3. 必须精确圈选时：**让用户在 UI 里刷/点**（选择主体、画笔），我们再改滑块——滑块本身是准的，错的只是坐标
4. 如果已经放错了：**直接 `remove_mask` 删掉**，不要试图挪位置（`set_mask_adjustments` 改不了几何，只能重建，而重建还是错）

> 💡 和坑 21 合起来看：**竖拍 = 坐标系陷阱**。裁切是"上下左右换轴"，蒙版是"位置乱飘"，两者都不能靠算术补偿，只能靠"导出验证 + 让用户在 UI 里做几何操作"。

<a id="pit-11"></a>
### 坑 11：导出的 `quality` 参数无效——但画质本来就是最高

**症状**

同一张图用 `quality: 10` 和 `quality: 100` 导出，文件字节数只差 **5 字节**（元数据差异）。

**但别再花时间修它。** 解析 JPEG 量化表（DQT）确认：亮度表几乎全是 1、最大值 3，色度表最大 3——**这是 JPEG 能表示的最精细量化，约等于画质 100**。你拿到的本来就是最高画质。

```powershell
python scripts/jpeg_quality.py exported.jpg
```

> 这是「**先测量，再决定要不要修**」的典型案例。如果只看参数没生效就去改代码，会浪费几个小时在一个不存在的问题上。

<a id="pit-1"></a>
### 坑 1：`ColorGrade*` 和 `SplitToning*` 不在允许列表

`@pired/lightroom-mcp` 的 `DEVELOP_SETTING_KEYS` 里**既没有三向分级的 `ColorGradeShadowHue` 这类键，也没有旧的 `SplitToning*` 键**。传了会报 `unknown property`。

**替代方案（而且更强）**：用**色调曲线分通道**。

- **蓝通道**：暗部抬 + 高光压 → 暗部偏青蓝、亮部去蓝
- **红通道**：暗部压 + 高光抬 → 阴影去红、高光转暖
- **绿通道**：暗部微抬 → 让阴影落在青绿而非纯蓝

曲线能精确控制过渡，**比分级滑块细腻得多**。

**验证某版本支持什么**：

```powershell
Select-String -Path "node_modules\@pired\lightroom-mcp\dist\tool-contracts.js" `
  -Pattern 'SplitToning|ColorGrade'
# 无输出 = 不支持
```

<a id="pit-7"></a>
### 坑 7：别假设用户想要「从干净底片重做」

用户的原片**已经带着他自己的调色**。虚拟副本的起点是**用户调过的状态**，不是 RAW 默认值。

- 想从干净起点做 → 必须先复位（[坑 3](#pit-3)）
- 不想推翻用户 → 直接在他基础上改
- **别自己猜**，问清楚：「延续你原来的方向」还是「基本重调」

**这条的另一面**：用户原来的参数**暴露了他的审美意图**，价值极高。读一下再决定：

| 观察到 | 推断 |
|---|---|
| `Highlights −77 / Shadows +45` | 很在意高光溢出，坚持打开暗部 |
| `Temperature 6250K` 对着阴天 | 在对抗现场冷光 |
| `HueAdjustmentAqua +67 / Blue +46` | 想把青蓝推向**紫**（冷紫调） |
| `Blacks −63` + 暗角 `−30` | 重对比的硬朗纪实感 |

**照搬不行**（用户可能就是不满意才让你调），但**完全无视更糟**。

### 坑 8：别用「压暗」冒充「电影感」

实测教训：把「冷青电影都市感」理解成重风格化 → 色温压到 4600K、黑阶 −22、整体欠曝，结果用户反馈「**太暗太蓝**」。

<a id="pit-13"></a>
### 坑 13：用户会在 Lightroom 里点错照片

**症状**

用户说「看不出来效果」——按 `Y` 前后毫无区别。

**根因**

虚拟副本默认跟原片**叠在一起**。如果原片和副本**都打了留用旗标**，筛选视图里会出现**两张同名照片**。用户点的是**从未被修改的原片**。

**怎么发现**

先确认用户点的是哪一张。**虚拟副本在缩略图右下角有一个折角图标**——这是最可靠的区分方式。

**根治**

把编辑过的副本 `add_to_collection` 到一个命名收藏夹（如 `AI精调_进行中`），**让用户直接打开那个收藏夹**，彻底避开歧义。

<a id="pit-17"></a>
### 坑 17：`CropAngle` 的符号约定

**`CropAngle` 增大 ＝ 画面逆时针旋转**，与 PIL 的 `rotate(+deg)` **同向**。

**实测方法**（值得学的思路）：把 Lightroom 渲染的图，分别与 PIL 已知旋转方向的两个参照做像素比对——MAD 差 5.1，**远大于噪声**，所以结论确定。不要靠猜符号。

<a id="pit-18"></a>
### 坑 18：高 ISO 的照片，降噪要和提亮一起考虑

**症状**

ISO 1600 的夜景，提亮阴影 +28 之后，100% 放大能看到明显的亮度噪点（「白点」）。

**怎么办**

**不要等用户放大发现再补。** 拿到照片先看 ISO，高 ISO 就在写影调的同时把 `LuminanceSmoothing` 一起设上。

实测配方：`luminance 40 / detail 40 / contrast 15 / color 30` 可降颗粒约 **50%** 而保住小字；推到 `52 / 32 / 22 / 34` 可降 **55~64%**，代价是小字开始发软。

## 技巧：用 HSL 当「免蒙版局部调整」

当画面里有**一种独占某个颜色的主体**时（例如红车身 vs 满画面的黄格线），**直接调那个颜色的 HSL**，效果等同于局部调整。

**优点**：

- **零蒙版风险**（不碰 [坑 9](#pit-9)）
- 边缘过渡天然自然，不会有蒙版抠图痕迹

**局限**：只有当目标颜色在画面里足够「独占」时才成立。
